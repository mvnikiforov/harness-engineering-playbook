# Практика: цепочка верификации в AILock-Step

В двух предыдущих разделах мы заложили принципы и механизмы верификации. В этом разделе мы продолжим разбирать кейс системы OKR из главы 02d и покажем, как эти механизмы реализуются на практике внутри фреймворка AILock-Step. В разделе 02d был показан полный путь спецификации от одной фразы до исполняемого документа. Здесь мы продолжим с того места, где остановились: как после завершения спецификации выстроить инфраструктуру верификации, как ее запускать и как перехватывать дрейф намерений (`Intent Drift`) до слияния кода.

Процесс разворачивается в три последовательных шага: определение API-контрактов в архитектурном документе (каркас верификации), генерация интеграционных тестов из спецификации (исполняемые ограничения) и запуск независимого агента для ревью на соответствие спецификации (перехват слепых зон, недоступных тестам).

## Шаг 1: Определение API-контракта

Спецификация из раздела 02d уже содержала таблицу API-контрактов из 6 эндпоинтов с указанием метода (Method), URL и параметров (Parameters). Эта таблица очерчивала границу взаимодействия между фронтендом и бэкендом, но не обладала достаточной детализацией для прямой генерации тестов.

Тестам недостаточно знать, что «такой эндпоинт существует». Им нужно точно знать, что он принимает на вход, что возвращает и при каких условиях отвечает ошибкой. На этапе подготовки архитектурного документа фреймворк разворачивает контракты в тестируемые спецификации интерфейсов. Возьмем для примера эндпоинт создания цели в системе OKR:

```yaml
POST /system/okrObjective:
  request:
    body:
      employeeId: { type: integer, required: true }
      quarter: { type: string, required: true, pattern: "YYYY-QN" }
      title: { type: string, required: true, maxLength: 200 }
  response:
    success: { code: 200, body: { msg: "新增成功", data: { objectiveId: integer } } }
    errors:
      - { condition: "title 为空", code: 500, msg: "目标标题不能为空" }
      - { condition: "quarter 格式不合法", code: 500, msg: "季度格式错误" }
```

Этот контракт выполняет три задачи. Во-первых, он задает тип и ограничения каждого поля (`title` с `maxLength: 200`, что соответствует ключевому правилу в спецификации). Во-вторых, он определяет структуру успешного ответа (согласованную с форматом `AjaxResult` фреймворка RuoYi, как зафиксировано в `project-context.md`). В-третьих, он перечисляет сценарии ошибок и соответствующие им тексты сообщений.

С таким контрактом на руках фронтенд-разработчики могут поднять mock-сервер для имитации бэкенда, а бэкенд-разработчики — напрямую тестировать эндпоинты, подавая на вход описанные в контракте параметры. Обе стороны ведут разработку независимо, сверяясь с единым контрактом.

## Шаг 2: Генерация интеграционных тестов из спецификации

Когда спецификация готова и контракт определен, наступает этап генерации тестов. Навык `/generate-tests` во фреймворке извлекает тест-кейсы из двух источников: критериев приемки и бизнес-правил в спецификации, а также спецификаций интерфейсов в API-контракте.

Тесты, сгенерированные по критериям приемки, проверяют поведение, наблюдаемое пользователем. В примере с системой OKR 13 критериев приемки и 5 бизнес-правил (всего 18 правил) отображаются в 7 сквозных (E2E) тест-кейсов. Это соответствие фиксируется явно:

```markdown
| Test Case | Covered Spec Items | Verification Content |
|-----------|--------------------|---------------------|
| test-01 | AC-1, BR-004 | Создание цели: валидация обязательных полей + квартал по умолчанию |
| test-02 | AC-2 | Список целей: фильтрация по кварталу и сотруднику |
| test-03 | AC-3 | Редактирование цели: изменение названия и статуса |
| test-04 | AC-4, BR-001 | Удаление цели: каскадное удаление связанных KR |
| test-05 | AC-5 | Список целей: отображение количества связанных KR |
| test-06 | BR-002, BR-003 | Ограничения KR: максимум 5 шт. + диапазон выполнения 0-100 |
| test-07 | BR-005 | Квартальный обзор: только чтение, отсутствие кнопки редактирования |
```

Сама эта таблица сопоставления служит документом трассируемости (traceability). Каждый критерий приемки прослеживается до конкретного тест-кейса, а каждый тест-кейс — обратно до пункта спецификации, который он проверяет. Если в будущем спецификация изменится (например, правило BR-005 будет удалено), таблица мгновенно покажет, какие именно тесты необходимо обновить.

Тесты, сгенерированные из API-контракта, проверяют поведение на уровне интерфейсов. В примере с эндпоинтом создания цели контракт задает ограничения для 3 полей и 2 сценария ошибок, которые напрямую транслируются в интерфейсные тесты:

```typescript
describe('POST /system/okrObjective', () => {
  test('成功创建目标', async () => {
    const res = await request.post('/system/okrObjective', {
      employeeId: 1,
      quarter: '2026-Q2',
      title: '提升客户满意度'
    });
    expect(res.body.code).toBe(200);
    expect(res.body.data).toHaveProperty('objectiveId');
  });

  test('title 为空时返回错误', async () => {
    const res = await request.post('/system/okrObjective', {
      employeeId: 1,
      quarter: '2026-Q2',
      title: ''
    });
    expect(res.body.code).toBe(500);
  });

  test('title 超过 200 字符时返回错误', async () => {
    const res = await request.post('/system/okrObjective', {
      employeeId: 1,
      quarter: '2026-Q2',
      title: 'x'.repeat(201)
    });
    expect(res.body.code).toBe(500);
  });
});
```

Эти тесты существуют еще до того, как агент приступит к написанию кода. Сначала все они падают (горят красным), поскольку эндпоинты еще не реализованы. Когда агент начинает писать код, завершение каждого эндпоинта запускает прогон тестов. Переход теста из красного состояния в зеленое означает продвижение вперед. Сохранение красного статуса сигнализирует об отклонении.

Обратите внимание: E2E-тесты и интерфейсные тесты работают на разных уровнях. E2E-тесты проверяют полные цепочки поведения с точки зрения пользователя. Интерфейсные тесты проверяют входы и выходы отдельных эндпоинтов с точки зрения контракта. Они дополняют друг друга: E2E-тесты выступают основным механизмом приемки, а интерфейсные тесты обеспечивают точную локализацию сбоев.

## Шаг 3: Code Review на соответствие спецификации

После того как агент завершает написание кода, навык `/review-against-spec` запускает независимую сессию ревью. Агент-ревьюер работает в чистом контексте, не имея никакой информации о том, как именно шел процесс кодирования. На вход он получает только изменения в коде и исходную спецификацию. На выходе формируется отчет о соответствии спецификации.

В примере с системой OKR после первого раунда генерации кода отчет агента-ревьюера выглядит следующим образом:

```markdown
## Spec Consistency Report

### Acceptance Criteria
| # | Criterion | Status | Evidence |
|---|-----------|--------|----------|
| AC-1 | 新增目标必须选择员工、季度、标题 | PASS | OkrObjectiveController.add() validates required fields |
| AC-4 | 删除目标同时删除关联 KR | PASS | @Transactional + keyResultMapper.deleteByObjectiveId() |
| ... | | | |

### Business Rules
| # | Rule | Status | Finding |
|---|------|--------|---------|
| BR-001 | 级联删除 | PASS | — |
| BR-002 | KR数量限制 max 5 | PARTIAL | Frontend has Element UI prompt, but backend ServiceImpl lacks count validation. Bypassing the frontend and calling the API directly can exceed the limit. |
| BR-003 | 完成率范围 0-100 | PASS | — |
| BR-004 | 默认季度 | FAIL | handleAdd() does not set a default value for form.quarter. The quarter dropdown is empty when the create dialog opens. |
| BR-005 | 总览只读 | PASS | — |

### Scope Check
- Detected modification to login.vue (+12 lines), but the spec does not involve the login module. Flagged as OUT_OF_SCOPE change.

### Summary
- AC: 13/13 PASS
- BR: 3/5 PASS, 1 PARTIAL, 1 FAIL
- Scope: 1 out-of-scope change detected
- Recommendation: Fix BR-002 and BR-004, then resubmit
```

Этот отчет наглядно демонстрирует, как `Code Review` закрывает слепые зоны, недоступные для тестов. Проблема с правилом BR-002 (отсутствие проверки количества KR на бэкенде) при тестировании маскируется поведением фронтенда: E2E-тесты действуют через пользовательский интерфейс, где подсказка фронтенда не дает добавить 6-й KR, поэтому тест проходит успешно, хотя уязвимость на бэкенде остается. Агент-ревьюер, поочередно сопоставляя пункты спецификации с кодом, обнаружил, что требование реализовано лишь наполовину.

Контроль границ задачи (Scope Check) — еще одна область, которую не способны покрыть тесты. Агент попутно изменил файл `login.vue`, однако тесты проверяют только страницы, связанные с OKR, и никак не затрагивают модуль авторизации. Просканировав diff, агент-ревьюер выявил изменение за пределами области спецификации и пометил его для проверки человеком.

## Полная цепочка верификации

Все три шага складываются в единую цепочку: контракт задает границы, тесты выстраивают поверх этих границ исполняемые ограничения, а `Code Review` перехватывает дрейф намерений, до которого не дотягиваются тесты. Человеку на ревью больше не нужно вычитывать сам код — достаточно изучить два отчета: результаты прогона тестов (корректно ли поведение?) и отчет о соответствии спецификации (соблюден ли замысел?). Оба отчета напрямую привязаны к структуре спецификации и фокусируют внимание на отклонениях и пробелах.

На этом этапе спецификация (глава 2) в связке с верификацией (эта глава) образуют замкнутый контур (`closed-loop control`) для отдельной задачи. Один инженер в паре с агентом способен надежно провести разработку отдельной функции по полному конвейеру: от спецификации до написания кода и слияния изменений.

Этот замкнутый контур служит фундаментом для всего дальнейшего масштабирования. Когда вы переходите к параллельному запуску нескольких агентов для разработки разных функций (тема Части II), контракты, тестовая инфраструктура и механизмы ревью, выстроенные в этой главе, превращаются из просто хорошей инженерной практики в необходимое условие выживания. Без контрактов результаты работы нескольких агентов при интеграции вступят в конфликт. Без тестовой инфраструктуры сбои после слияния невозможно локализовать до конкретного модуля. Без независимого ревью пропускная способность человека станет узким горлышком перед скоростью работы нескольких агентов.
