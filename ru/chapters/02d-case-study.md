# На практике: рабочий процесс AILock-Step Feature Workflow

В предыдущих разделах мы заложили методологический фундамент работы со спецификациями: разделение информации на слои, три измерения, перекрестную валидацию и итерационный цикл. В этом разделе мы на примере конкретной системы покажем, как эти концепции воплощаются в реальной инженерной практике.

AILock-Step Feature Workflow — это документно-ориентированный фреймворк разработки поверх Claude Code, созданный участником нашего сообщества. Он использует навыки (skills / слеш-команды) для оркестрации всего жизненного цикла разработки функции — от приема исходного требования до сдачи готового кода. С помощью этой системы в проекте платформы ИИ-агентов было успешно выпущено более 40 функций. Полный исходный код фреймворка открыт и доступен на GitHub.

Описанное ниже — один из вариантов реализации, а не единственно возможный эталон. Наша цель — не скопировать структуру директорий или формат конфигурационных файлов, а увидеть, как разобранные выше принципы превращаются в работающий инженерный конвейер.

## Послойная организация информации на практике

Ранее мы выделили четыре информационных слоя (видение, архитектуру, функцию и задачу) и отметили, что разные слои меняются с разной скоростью, имеют разную область применимости и должны храниться в отдельных документах с собственными стратегиями загрузки. В AILock-Step эта слоистая архитектура реализована через три категории документов.

**`CLAUDE.md` хранит сквозные обязательные ограничения.** Этот файл Claude Code автоматически загружает при каждом запуске. Его содержимое — жесткие правила, которые практически не меняются на протяжении всей жизни проекта: обязательное использование строгого режима TypeScript (`strict`), запрет на прямые обращения к базе данных в обход ORM, единый формат сообщений коммитов, запрет на жестко закодированные (hardcoded) параметры конфигурации. Эти ограничения не принадлежат какому-то одному слою — они пронизывают все уровни, и им должна подчиняться любая задача. Поскольку эти правила стабильны и нужны всегда, они размещаются в файле с автоматической постоянной загрузкой.

**`project-context.md` хранит верхнеуровневую информацию.** Он соответствует слоям видения и архитектуры. Его структура выглядит так:

```
Technology Stack
  | Category | Technology | Version | Notes |
  | Frontend | React      | 18.x    | ...   |
  | Backend  | Node.js    | 20.x    | ...   |
  | Database | PostgreSQL | 15      | ...   |

Directory Structure
  src/
  ├── components/     # Shared components
  ├── pages/          # Page routes
  ├── services/       # API services
  ├── hooks/          # Custom hooks
  └── utils/          # Utility functions

Critical Rules
  Must Follow:
  - All API responses use the unified ResponseWrapper format
  - Database operations must go through the ORM layer; raw SQL is prohibited
  Must Avoid:
  - Do not call the database directly from components
  - Do not put business logic in utils/

Code Patterns
  Naming conventions, import style, error handling patterns

Testing Patterns
  Unit test location, naming rules, E2E framework

Recent Changes
  Changes and impact from the most recent features
```

У этого документа есть жесткое ограничение: максимум 200 строк. Этот лимит напрямую вытекает из ограничений контекстного окна, о которых мы говорили ранее. Контекст проекта загружается в память агента при каждой сессии. Если он разрастется, то начнет вытеснять место, необходимое для спецификаций и самого кода. Двухсот строк вполне достаточно, чтобы вместить ключевые сведения о проекте среднего размера, но такой лимит дисциплинирует: вы включаете в файл только оглавление и ориентиры верхнего уровня, не перегружая его деталями реализации.

Этот документ не пишется один раз и навсегда. После завершения каждой новой функции, если в проект добавились новые компоненты стека, паттерны кода или разделы файловой структуры, `project-context.md` инкрементально обновляется. В нижней части файла ведется журнал изменений (changelog) с датой и кратким описанием каждой правки. Это в точности отражает сформулированное ранее свойство: «верхнеуровневая информация меняется редко, но периодически обновляется».

**У каждой функции есть собственный независимый комплект из трех документов: `spec.md`, `task.md` и `checklist.md`.** Они отвечают за слои функции и задачи. Эти файлы подгружаются в контекст только тогда, когда агент непосредственно работает над данной функцией, и отправляются в архив сразу после ее завершения.

Стратегия загрузки в такой трехуровневой схеме предельно прозрачна: `CLAUDE.md` и `project-context.md` загружаются всегда (это общий фон, необходимый для любой задачи), а документы конкретной функции подгружаются только на время ее выполнения (загрузка документации от посторонних функций создавала бы лишь информационный шум).

## Три измерения в шаблоне спецификации

Шаблон `spec.md` в AILock-Step переводит три теоретических измерения (намерение, приемку и ограничения) в конкретные поля документа.

**Измерение намерения** представлено в трех полях. Поле «Описание требования» (Requirement Description) на естественном языке фиксирует, какая именно проблема решается. Поле «Точки пользовательской ценности» (User Value Points) содержит список независимых полезных результатов, которые приносит эта функция; этот список формируется в ходе анализа задачи агентом. Поле «Пользовательская история» (User Story) использует стандартную формулу: *Как [роль], я хочу [цель], чтобы [ценность]*.

**Измерение приемки** выражается через сценарии на языке Gherkin. Шаблон требует сгенерировать как минимум один сценарий успешного выполнения (happy path) и один сценарий обработки ошибки для каждой точки пользовательской ценности. Например, для функции регистрации пользователя будут созданы два сценария:

```gherkin
# Scenario 1: Successful registration
Given the user is on the registration page
When the user enters a valid username "testuser" and password "Test123!"
And clicks the register button
Then the account is created successfully
And a welcome message is displayed

# Scenario 2: Duplicate username
Given the user is on the registration page
And the username "testuser" already exists
When the user enters the username "testuser" and password "Test123!"
And clicks the register button
Then the error message "Username already exists" is displayed
```

Эти сценарии — измерение приемки в действии: каждый из них проверяет, соответствует ли поведение функции заложенному намерению. Успешный сценарий подтверждает, что «система делает то, что должна». Сценарий ошибки гарантирует, что «при возникновении проблем система ведет себя предсказуемо и корректно».

**Измерение ограничений** сосредоточено в поле «Анализ контекста» (Context Analysis), состоящем из трех подразделов: эталонный код (существующие модули проекта, доступные для переиспользования), связанная документация (проектные описания, документация API) и связанные исторические требования (похожие функции, реализованные в прошлом). Это поле задает агенту исходный контекст и границы изменений: что уже есть под рукой, как подобные задачи решались раньше и какие участки трогать не следует.

Кроме того, в шаблоне предусмотрено поле «Технический подход» (Technical Approach) с пометкой «заполняется в ходе разработки». На этапе генерации спецификации оно остается пустым и заполняется конкретным планом реализации только тогда, когда агент приступает к написанию кода. Это соответствует принципу послойного управления информацией: «низкоуровневые детали генерируются только в момент реальной необходимости».

## Перекрестная валидация на практике

Три документа (`spec`, список задач, чек-лист) и их роли напрямую реализуют механизм перекрестной валидации.

Спецификация (`spec.md`) — это первая интерпретация: отталкиваясь от исходного требования, агент формирует описание намерения, сценарии приемки и анализ ограничений.

Список задач (`task.md`) — вторая интерпретация: опираясь на спецификацию, агент декомпозирует работу на конкретные шаги выполнения. Шаблон группирует задачи по четырем категориям (модули/компоненты, эндпоинты API, страницы фронтенда, прочее), оформляя каждый шаг в виде чекбокса. Внизу документа расположена таблица отслеживания прогресса, которую агент обновляет по мере выполнения работы.

Чек-лист (`checklist.md`) — третья интерпретация: отталкиваясь от того, «как это сделать», агент рассуждает в обратном направлении — «как убедиться, что все сделано правильно». Шаблон включает пять категорий проверок: полнота разработки (все ли задачи закрыты, обработаны ли граничные случаи), качество кода (соблюден ли единый стиль, нет ли «запахов кода»), тестирование (написаны ли модульные тесты, проходят ли они), документация (заполнено ли поле технического подхода в `spec.md`, обновлены ли связанные документы) и готовность к коммиту (проиндексированы ли изменения в git, подготовлено ли сообщение коммита).

Если в чек-листе всплывает пункт проверки, о котором в спецификации не было ни слова, значит, на этапе планирования задач агент добавил от себя функциональность, не предусмотренную спецификацией. Если пункт чек-листа противоречит формулировкам спецификации, значит, при передаче между слоями произошел сдвиг намерения. Полная согласованность всех трех документов служит надежным подтверждением того, что намерение выровнено.

## Процесс декомпозиции на практике

Когда навык `/new-feature` определяет, что требование содержит три и более точек пользовательской ценности, система рекомендует разделить задачу. Этот механизм подробно зафиксирован в тестах фреймворка.

На вход подается требование: «Система аутентификации пользователей с поддержкой регистрации, входа и управления правами доступа». Агент выделяет три независимые точки пользовательской ценности: регистрацию пользователя (создание новой учетной записи), вход в систему (получение доступа) и управление правами (контроль привилегий доступа). Поскольку число точек ценности достигло 3, срабатывает триггер рекомендации разбиения.

Система предлагает план декомпозиции: исходное требование делится на три подфункции — `feat-auth-register` (регистрация пользователя, без зависимостей), `feat-auth-login` (вход пользователя, зависит от `feat-auth-register`) и `feat-auth-permission` (управление правами, зависит от `feat-auth-login`). Связи зависимостей между ними система выстраивает автоматически.

После подтверждения разбиения система создает для каждой подфункции отдельную директорию с собственным комплектом файлов `spec.md`, `task.md` и `checklist.md`. Одновременно в файл `queue.yaml` записываются статусы, приоритеты и граф зависимостей всех трех подфункций, а также создается запись родительского требования для отслеживания общего прогресса.

Перед запуском любой функции в работу движок выполнения проверяет, закрыты ли все ее зависимости. Если попытаться запустить `feat-auth-login` до того, как завершена `feat-auth-register`, система заблокирует старт и выведет сообщение «зависимости не удовлетворены» (`dependencies not satisfied`).

Далее каждая подфункция проходит по стандартному итерационному циклу: разворачивание спецификации агентом, перекрестная валидация, ревью пользовательской истории человеком и — после достижения сходимости — переход к написанию кода.

## Реальные затраты времени человека

На протяжении всего рабочего процесса личное время разработчика концентрируется в одной-единственной точке: вычитке пользовательской истории и сценариев Gherkin сразу после генерации спецификации. Разработчик проверяет, совпадает ли понимание агентом того, «кому помогает эта функция и какую проблему она решает», с его собственным замыслом. Если понимание совпадает, человек передает эстафету агенту, позволяя ему самостоятельно выполнить декомпозицию на задачи, сгенерировать чек-лист и написать код.

Это на практике подтверждает описанную выше роль человека: выравнивание намерений способен оценить только человек, тогда как проверку внутренней согласованности можно делегировать агенту. Внимание разработчика сфокусировано на контрольной точке с максимальной отдачей (проверке направления на верхнем уровне), а перекрестная валидация агента страхует консистентность на нижних этапах.

Полный исходный код этой реализации открыт на GitHub ([AILock-Step Feature Workflow](https://github.com/auenger/AILock-Step/tree/feature/dev-agent-subagent-optimization/feature-workflow)). Показанная здесь система — лишь один из возможных способов организации работы. Читателям необязательно использовать тот же инструмент или в точности повторять структуру директорий. Главное — усвоить стоящие за этим инженерные принципы: послойное управление информацией, четкое описание каждого слоя в трех измерениях, перекрестную валидацию для перехвата межслойного дрейфа и итерационную доводку до сходимости. Какими именно инструментами воплощать эти принципы — зависит от специфики вашего проекта и команды.

## Резюме главы

Суть спецификации — в выравнивании намерений (Intent Alignment). Режим Vibe Coding терпит неудачу, потому что намерение живет внутри диалога, а диалог — это среда, которая разрастается, накапливает внутренние противоречия и теряет содержимое. Ограниченное контекстное окно агента и неравномерное распределение внимания превращают согласование намерений из коммуникационной задачи в инженерную.

Решение этой инженерной задачи опирается на два фундаментальных принципа. Во-первых, информация естественным образом делится на слои с разной частотой изменений и разной широтой применимости. Их необходимо структурированно разносить по разным документам: верхнеуровневая информация загружается в контекст постоянно, а данные уровня задачи подгружаются по требованию. Во-вторых, на каждом слое содержимое четко формулируется в трех измерениях (намерение, приемка, ограничения), где ключевая задача измерения приемки — вовремя обнаружить потерю согласованности с вышестоящим слоем.

Спецификация создается итеративно. Вы фиксируете исходное намерение, агент разворачивает черновик, перекрестная валидация вскрывает расхождения, вы вносите правки или декомпозируете задачу, проводите повторную проверку и повторяете цикл до полной сходимости. В этом цикле вынести суждение о том, удалось ли выровнять намерения, может только человек, поскольку само намерение существует исключительно в его голове. А то, насколько глубоким и строгим должен быть этот цикл, определяется ценой ошибки и стоимостью последующей переделки.

Спецификация решает задачу «что именно нужно построить». Но даже безупречная спецификация сама по себе не гарантирует, что написанный по ней код будет работать без ошибок. Тому, как надежно проверять корректность сгенерированного агентом кода, посвящена следующая глава.
